# 本地模型（Ollama）接入实测

> 日期：2026-09-30 ｜ 机器：Windows 本机 ｜ 模型：`qwen3:4b-instruct-2507-q4_K_M`（4B / Q4_K_M / 2.5GB）
> 目的：把「零 API 消耗」的开发与回归通道打通，让改动可以免费迭代。
> **结论：链路完全可用、零代码改动；但 4B 模型在「逻辑审计员」一路上系统性失效，不能直接替代云端模型做现场使用。**

---

## 1. 怎么接（零代码改动）

mavis 的 `OpenAIProvider` 本来就是 OpenAI 协议，而 Ollama 提供 OpenAI 兼容端点，
所以只需把 `LLM_BRIDGE_URL` 从协议桥改指 Ollama 即可：

```bash
export LLM_BRIDGE_URL=http://127.0.0.1:11434/v1
export LLM_MODEL=qwen3:4b-instruct-2507-q4_K_M
```

`backend/app/config.py` 的 `LLM_BRIDGE_URL` / `LLM_MODEL` 都读环境变量，
`mavis_bridge.py` 把它当 `base_url` 传给 `create_llm_provider` —— **不需要动任何源码**。

已封装成脚本：`bash scripts/run_local.sh`（内含 Ollama 探活与并发预设）。

> **本模式下协议桥（8011）不参与。** 桥的存在是为了翻译 Anthropic 协议 + 修复 JSON 形状；
> 而 Ollama 的 OpenAI 端点原生支持 `response_format=json_schema`（实测见 §2），
> 这两个职责都不需要了。
>
> 顺带提醒：本机 curl 访问 `127.0.0.1` 会被系统代理拦成 `os error 10061`，
> 探活/调试本地端口一律加 `--noproxy '*'`。

## 2. 结构化输出实测（决定方案可行性的那一项）

mavis 的结构化输出**依赖** `response_format: json_schema`。实测 Ollama 完全支持：

```
POST /v1/chat/completions
  response_format = {"type":"json_schema","json_schema":{"name":"AuditorOut","schema":<pydantic schema>}}

→ {"res": []}            # 严格 JSON，顶层带 res —— 正是 mavis 要的形状
```

对比：协议桥之所以必须做「schema 写进系统提示 + JSON 形状修复」，
是因为 **Anthropic 协议没有 `response_format` 字段**。
接 Ollama 时这条上游约束不存在，问题自然消失。

## 3. 延迟实测（五路并行，热态）

首次调用 15.68s（模型加载），之后为热态。下表是模型已加载后的连续两次采样之一：

| 参谋 | 延迟 | 状态 |
|---|---|---|
| 质询手 | 1.19s | ok |
| 逻辑审计员 | 1.43s | **empty** |
| 解释方法策略师 | 4.15s | ok |
| 反驳手 | 7.77s | ok |
| 风险提示员 | 9.72s | ok |
| **总墙钟** | **9.74s** | = 最慢一路 |

- 总耗时 ≈ 最慢那一路 ⇒ **确实是真并行**，没有被 `LLM_CONCURRENCY` 卡住
  （前几路 1–4s 就完成并释放了信号量，最慢那一路早已占位）。
- 对照云端（`docs/spike-0-report.md`）：deepseek-chat 三路并行 1.34s。
  本地 4B 慢约 7 倍，但**成本为零**，且仍在默认 20s 预算内。

## 4. 质量实测（关键差异所在）

| 参谋 | 判断 | 具体表现 |
|---|---|---|
| 反驳手 | 🟡 结构对、引用可疑 | 产出 2 条完整涵摄三段式。但引用的《著作权法》第 11/12 条**内容与真实法条不符**，且**没有按指令写「待核验」** |
| 质询手 | ✅ 可用 | 3 个问题，可直接抛 |
| 逻辑审计员 | ❌ **失效** | 连续 3 次返回 `{"res": []}`，见 §5 |
| 解释方法策略师 | ✅ 可用 | 正确识别「对方用文义解释 → 我方主张目的解释优先」 |
| 风险提示员 | ✅ 可用 | 3 条风险，分类（我方薄弱 / 法源不稳 / 事实不清）准确 |

**引用核验**：`《著作权法》第11条`、`第12条` 均判 `unverified`（`retriever: null`）——
因为 `data/corpus/` 还是空的。**这正好说明引用核验的价值**：
模型编造法条内容时，只有程序化核对能拦住它，模型自己的「待核验」自觉不可靠。

## 5. 审计员失效的证据（本节最重要）

两个用例，直接用 Ollama 带 schema 调用，看**模型原始输出**（排除解析环节的干扰）：

| 用例 | 对方发言 | 模型原始输出 |
|---|---|---|
| 案例 1 | 「著作权法只保护自然人的智力成果，AI 不是人，所以 AI 生成内容不应享有著作权。」 | `{"res": []}` |
| 案例 2 | 「隔壁老王用 AI 写了本书结果没人买，可见 AI 创作没有价值，所以所有 AI 生成物都不配受保护。」 | `{"res": []}` |

案例 2 是教科书级的**以偏概全 + 滑坡**（个例 → 全称否定；销量 → 权利资格），
4B 模型仍然返回空列表。

**定性**：
- 这不是代码 bug —— 链路、schema、解析全部正常（`[mavis 链路] 返回类型=list 内容=0`，与模型输出一致）。
- 也不是被「宁可空列表」的纪律压住的保守 —— 它连明显谬误都没看见。
- **是 4B 模型在「识别逻辑谬误」这类任务上的能力下限。**
  对照 `docs/spike-0-report.md`：deepseek-chat 同一任务能准确指认「偷换概念」。

> ⚠️ 样本量 = 2 个用例 × 单次采样，不足以做严谨评估（温度非 0）。
> 但「连续多次返回完全空」这个方向性信号足够明确，不宜带病投入现场使用。

## 6. 并发数的正确理解（修正一处此前的判断）

早前记过一条「`LLM_CONCURRENCY` 默认 4 < 5 路，是真缺陷」。本次实测后需要**修正**：

- mavis 的 `_GLOBAL_SEM` 是**进程级**信号量，确实会把并发压到 4。
- **但对本地 Ollama，压并发是对的**：单实例推理，并发超了只会排队，还抢显存
  （mavis 源码注释原话：「Ollama 单实例并发有限，超了只会排队无收益」）。
  `scripts/run_local.sh` 因此把本地并发预设为 **2**。
- **只有接云端网关时**，才应该把 `LLM_CONCURRENCY` 提到 ≥ 参谋路数，
  否则第 5 路要等第一批释放，总耗时翻倍。

⇒ 结论：这不是一个「改个数字」的缺陷，而是**两种上游需要两套预设**。已分别在脚本与文档里固化。

## 7. 建议的用途边界

| 用途 | 本地 4B 够用吗 |
|---|---|
| 链路自检、端到端回归、前端联调 | ✅ 完全够用，且零成本 |
| 改 prompt / 改 schema 后的快速验证 | ✅ 够用（结构正确性可验证，质量不可信） |
| 评估「变动是否变好」 | 🟡 只能看结构与延迟，**质量判断仍须云端模型** |
| 现场实战 | ❌ **不行**（审计员失效是无法接受的缺口） |

**下一步可选**：换更大的本地模型（如 qwen3:8b / 14b）再测审计员一路，
即可确认这堵墙是「4B 的能力下限」还是「整个本地路线的通病」。
