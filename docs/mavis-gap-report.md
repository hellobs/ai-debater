## 摘要

框架在自身示例中可运行，并不蕴含其能够在具备**并发约束、时限预算与失败语义**的生产链路中承重。本文以 ai-debater 为案例，对 mavis v1.3.3 进行一次可在仓库内完整复现的实地检验，回答三个问题：(i) 框架的哪些能力面可被实际承载；(ii) 哪些能力面存在架构性不适用；(iii) 其公开接口在承载过程中暴露了何种缺口。

检验在**只读约束**下进行，即受测仓库一行未改。该约束是结论有效性的前提：唯有如此，所有观测才能归因于框架本身，而非接入方的改动。

结果表明：mavis 的**基础设施半边**（模型接入、提示词模板、插件总线）可被完整承载，且其中若干设计（失败哨兵 `failsafe`、逐插件错误隔离）承担了不可替代的功能；其**仿真半边**（`Agent` / `Game` / `Simulator` / 记忆 / 日程 / 空间）与本案例的任务形态存在架构性错位。在此基础上，本文识别出 12 处缺口（G1–G12）与 6 条接线注意（N1–N6），并按严重度分级，给出与框架既有扩展约定相容的改进建议。首轮（§3.3 G1–G7 / §3.4 N1–N4）覆盖模型接入与模板/插件两扩展面的主链路；二轮（§3.3b G8–G12 / §3.4b N5–N6）沿同一条生产链路继续深挖协议适配、输出控制与宿主集成面。

**关键词**：生成式智能体；框架评估；实地检验；接口契约；失败语义；可复现性

## 1. 研究问题

### 1.1 问题的来源

ai-debater 是一个多智能体辩论参谋平台：给定辩题、我方立场与对方发言，并行调度五路参谋智能体，各自产出一类建议（反驳要点、质询问题、逻辑谬误指认、衡量尺度之争、风险提示），全部结果在时限预算内交付，其取舍由人类决策者完成。该形态对底层框架提出了四项约束：

1. **并发**：五路请求须同时发起，总墙钟接近最慢一路的耗时；
2. **时限**：须在预算到期时交付已就绪的部分，而非等待全部完成；
3. **失败可分辨**：须能区分"上游不可达"与"模型返回空内容"——二者对现场决策的意义相反；
4. **可观测**：须能按调用方（即按参谋）分别统计成功与失败。

这四项约束构成了评估 mavis 的判据：一个能力面是否"可用"，取决于其能否在上述约束下成立。

### 1.2 研究问题

- **RQ1**：mavis 的哪些能力面可被本案例完整承载，承载过程中哪些设计承担了不可替代的功能？
- **RQ2**：哪些能力面存在架构性不适用？该不适用是配置问题还是设计前提问题？
- **RQ3**：在承载过程中，其公开接口暴露了哪些缺口，严重度如何？

### 1.3 与既有版本的关系

本报告的前一版本结论为"mavis 仅作为模型接入层使用"，且只调用了 `create_llm_provider().completion()` 的 3 个参数（`prompt` / `return_type` / `retry`）。该版本存在**评估范围过窄**的缺陷：以"未使用"反推"不可用"，混淆了框架的能力边界与接入方的使用深度。本次检验扩大了承载范围，逐个能力面给出使用与否及其理由，并逐条记录缺口。

## 2. 研究设计

### 2.1 受测版本与安装形态

受测版本为 mavis v1.3.3（commit `511dea0`），以 editable 方式安装于项目 venv，`direct_url.json` 指向本地克隆路径（形如 `file:///<mavis 克隆路径>`）。版本号可通过框架自身暴露的 `mavisframework.__version__` 读取（该属性存在且取值正确，属于可用的元信息面）。

### 2.2 只读约束

**受测仓库在检验全过程中零改动。** 本文不采用 fork、monkey patch 或子类覆写等修改手段。该约束的意义在于保证**内部效度**：若允许改动框架，则所有观测都无法区分"框架的能力"与"改动后的能力"，结论对框架本身失效。

与之配套，本案例在工程上以测试强制维持边界：`backend/app/` 下仅 `mavis_bridge.py` 允许 `import mavisframework`，由 AST 扫描的单元测试守护；并使用第二个测试限定只允许访问顶层 / `plugin` / `prompt` 三个公开路径，禁止触达 `runtime.llm` 等内部模块。

### 2.3 判定标准

**能力面"被承载"的操作性定义**：该面存在一个公开入口，被本案例的**生产代码路径**调用（而非仅在探针中调用），且其语义与 §1.1 的四项约束相容。

**缺口"成立"的操作性定义**：满足以下三点之一，且可由探针稳定复现：

- **正确性缺口**：在正常使用下产生静默的错误行为（不抛异常，但结果偏离预期）；
- **可用性缺口**：使某项合理需求无法表达，或必须以额外代价绕过；
- **文档 / 人体工程缺口**：契约未文档化、或公开入口的成本显著高于其功能。

严重度分级：**高**（正确性，静默行为偏差）；**中**（可用性或可观测性受损）；**低**（文档与人体工程）。

### 2.4 检验工具

检验以 `backend/spikes/mavis_bounds.py` 为统一入口。该脚本为**只读探针**，不修改受测仓库任何文件，逐条复现 §3.3 与 §3.4 的全部结论，并打印实测中间量（如信号量对象同一性、退避参数序列、`get_summary()` 的原始返回）。报告中的所有数值均来自该脚本的实际输出，未作估算。

## 3. 结果

### 3.1 RQ1：可用面（三面用满）

| # | 能力面 | 框架入口 | 本案例落点 | 实际承载的功能 |
|---|---|---|---|---|
| 1 | 模型接入 | `create_llm_provider()` → `LLMProvider` | `backend/app/mavis_bridge.py` | `completion()` 的 `caller` / `failsafe` / `callback` 三参数；`is_available()` / `get_summary()` / `cache_stats()` 接入健康检查；框架内置的 90 s 超时与进程级并发闸 |
| 2 | 提示词模板 | `prompt.Scratch.build_prompt()` | `prompts/*.txt` + `advisors/base.py` | 三层模板（`layout` / `roles/*` / `tasks/*`），提示词由 Python 字符串常量转为可版本控制、可逐参谋覆盖的数据资产；启动期自检 `preload()` |
| 3 | 插件总线 | `plugin.PluginManager` | `backend/app/observers.py` | 三个观察者（`LedgerPlugin` / `StreamPlugin` / `MetricsPlugin`），获得逐插件错误隔离与 `setup / emit / teardown` 生命周期 |

#### 3.1.1 承担不可替代功能的两个设计

**（a）`failsafe` 参数是区分两类失败的充分手段。** 框架的 `completion()` 捕获全部异常（见 G3）。默认 `failsafe=None` 时，两类失败的返回值并非完全一致（上游重试耗尽返回 `None`，模型返回空内容返回 `''`），但该差别属**实现副产品**：任何按空值归并结果的调用方都会把二者收进同一分支 —— 本案例的判定顺序即如此（`out is None or len(out) == 0` → `empty`，见 N1）。传入私有哨兵对象 `FAILED` 后，"上游重试耗尽"成为一个**可比较的身份**，两类失败被分离为两个语义明确的状态：

| 返回值 | 本案例状态 | 语义 |
|---|---|---|
| `FAILED` 哨兵 | `error` | 上游连接失败或超时，重试已耗尽 |
| `None` / `[]` / `""` | `empty` | 上游应答正常，内容为空 |

该参数在框架的抽象基类签名中已经存在，属于"使用方式问题"而非能力缺失；但其**必要性未在文档中被提示**（见 N1）。

**（b）`callback` 的返回语义约束了规整策略。** 框架将 callback 返回 `None` 解释为"本次结果不计入，重试一次"。因此若在 callback 中执行内容否决，会把一次"质量偏低"放大为 `retry` 倍的上游调用。本案例据此将 `Advisor.adapt()` 的职责限定为归一化（去空白、丢弃整条空条目），不做质量判分。这是对框架语义的**顺从**而非绕过。

#### 3.1.2 插件总线替换内联回调链的实证

替换前的实现将"落库、推流、指标"三者串接于单个回调函数中，任一处抛出异常即中断后续环节。经 `PluginManager` 承载后，指标插件抛出异常仅产生一条 warning，落库与推流照常完成。该性质由 `tests/test_mavis_usage.py::test_single_plugin_failure_does_not_lose_other_results` 与 `::test_plugin_manager_isolates_a_failing_plugin` 固定。

### 3.2 RQ2：不适用面（仿真半边）

不适用面为 `Agent` / `Game` / `Simulator` / 记忆 / 日程 / 空间。**该不适用属架构性错位，而非配置不足**，判据有二：

1. **调度语义不一致**。`Simulator` 的语义是"在每一仿真步内驱动全部 Agent 走一遍生活仿真管线"，而本案例的需求是"并行执行一组彼此无状态依赖的单轮问答"。前者是有状态的、按步推进的时间演化过程；后者是无状态的、以墙钟时限为界的并行分发。二者在调度层无法互相归约。
2. **产物类型不一致**。`Agent.think()` 执行"日程 → 感知 → 行动决策 → 移动 → 计划 → 反思"的管线，其产物为**行动计划**；而本案例的需求产物是**供人类判断的建议文本**。框架仅识别其内置的 `prompt_*` 集合（`wake_up` / `schedule_*` / `generate_chat` / `reflect_*` 等），其中不存在"生成建议"这一类别，且该集合由框架硬编码，无法通过模板替换扩展。

方法论上，该结论的得出过程本身构成证据：在尝试将 `Agent` 塑形为"参谋"的过程中，每修复一处隐式接口依赖（计时器方法 → `tile.events` → 空 spatial tree 触发 `IndexError`）即浮现下一处，收敛迹象缺如。过程的完整记录见 `docs/spike-0-report.md`。

### 3.3 RQ3：缺口（G1–G7）

每条缺口按"现象 → 证据 → 对本案例的影响 → 应对 → 建议"五段式记录。所有建议均遵循框架自身的扩展约定：**纯新增、默认关闭、语义中立、附单元测试**。

#### G1 结果缓存的调用名白名单为硬编码

- **严重度**：中（可用性）｜**影响本案例**
- **现象**：结果缓存仅对框架内部写死的三个调用名生效，接入方无法将其确定性调用纳入缓存。
- **证据**：`runtime/llm_providers.py:107-111` 的 `_CACHEABLE_CALLERS` 为硬编码集合；`:60-65` 仅在 `caller in self._CACHEABLE_CALLERS` 时计算缓存键。实测：

  ```
  白名单: ['generate_chat_check_repeat', 'poignancy_chat', 'poignancy_event']
  caller='poignancy_chat'  同 prompt 调两次 → 上游被调 1 次（命中）
  caller='rebutter'        同 prompt 调两次 → 上游被调 2 次（不命中）
  ```

- **对本案例的影响**："同辩题 + 同对方发言 + 同我方台账"的重复分析在语义上是确定性的，本应命中缓存，现需重复消耗 5 次上游调用。现场场景中"再生成一次"是高频操作。
- **应对**：`cache=False`，如实关闭并在健康检查与前端仪表中显式标注"结果缓存未启用"，不制造缓存生效的表象。
- **建议**：增设 `cacheable_callers` 配置项（默认维持原三项），或提供 `provider.register_cacheable(caller)`。属纯新增，默认行为不变。

#### G2 全局并发闸为类属性，size 变更导致整体重建

- **严重度**：**高**（正确性）｜本案例经单例复用规避，暂不受影响
- **现象**：`_semaphore(size)` 在检测到 size 与上次不同时直接替换为一个新的 `threading.Semaphore`。其后果是：两个 `concurrency` 取值不同的 provider 会互相顶替对方的闸门，且**不产生任何异常或警告**。
- **证据**：`runtime/llm_providers.py:28-35`。实测：

  ```
  _semaphore(4) 两次是同一对象：True
  换成 8 再回到 4，还是当初那个吗：False
  ```

- **对本案例的影响**：当前不受影响——`mavis_bridge.get_provider()` 强制单例，全进程仅一个 provider。但该性质是"进程级闸门"与"实例级配置"之间的语义错配：在多 provider 场景下，限流将静默降级（在单实例推理服务上等价于"排队"变为"并发"）。
- **应对**：强制复用单例 provider，并在 `get_provider()` 的 docstring 中写明复用理由，防止后续维护者改为多实例。
- **建议**：信号量按 size 分桶（`dict[size, Semaphore]`），或将 size 固化为进程级配置、不再随实例变化。

#### G3 异常全捕获与退避硬编码

- **严重度**：中（可用性 / 可观测性）｜**影响本案例**
- **现象**：`completion()` 捕获全部异常后 `continue`，重试耗尽返回 `failsafe`；每次重试之间固定 `time.sleep(5)`。
- **证据**：`runtime/llm_providers.py:81-95`。实测（retry=3）：

  ```
  failsafe=None       → 返回 None        上游被调 3 次，退避 sleep 参数 [5, 5, 5]
  failsafe='SENTINEL' → 返回 'SENTINEL'  上游被调 3 次，退避 sleep 参数 [5, 5, 5]
  ```

- **对本案例的影响**：两个层面。① 失败信号丢失——不传 `failsafe` 则两类失败落进同一分支（见 §3.1.1a 与 N1）；② 退避时间与预算冲突——`retry` 取框架默认值 10 时，最坏情形需先睡眠 50 s 才放弃，而本案例的 `ADVISOR_BUDGET_S` 默认为 20 s，超时标记根本不会触发。
- **应对**：将 `retry` 显式压至 2（最坏 10 s，仍在预算内），并传入 `failsafe` 哨兵。
- **建议**：将退避参数化为 `completion(..., backoff: float = 5)` 或读取配置；提供 `raise_on_error=True` 以允许调用方自行决定是否吞掉异常。

#### G4 `prompt` 与 `plugin` 两个扩展面未进入顶层 `__all__`

- **严重度**：中（可用性）｜**影响接入方**
- **现象**：`mavisframework/__init__.py` 的文档声明其为"顶层 API 一览（推荐用法）"，但其导出项仅涵盖 config / core / scene / runtime / protocol；提示词面与插件面不在其中，只能按模块路径导入。
- **证据**：实测

  ```
  Scratch        在顶层 __all__ 里：False；顶层直接可访问：False
  Plugin         在顶层 __all__ 里：False；顶层直接可访问：False
  PluginManager  在顶层 __all__ 里：False；顶层直接可访问：False
  ```

  与此同时，`prompt/__init__.py` 的 `__all__ = ["Scratch", "Result"]`、`plugin.py` 的模块头声明"任何外部包都能作为插件挂进 mavis"——即**公开性是已声明的，但入口不在推荐位置上**。
- **对本案例的影响**：接入方依据"推荐用法"检索扩展入口时会失败，可能转而导入 `runtime.*` 内部模块。本案例的前一版本实现即采用了 `from mavisframework.runtime.llm import create_llm_provider` 这一非公开路径。
- **应对**：按模块路径导入 `mavisframework.plugin` / `mavisframework.prompt`，并以测试将"仅使用这三个公开路径"固定下来。
- **建议**：将 `Plugin` / `PluginManager` / `Scratch` 加入顶层 `__all__`。

#### G5 `validate_message()` 与 `PluginManager.emit()` 的契约不一致

- **严重度**：低（文档）｜已绕开
- **现象**：协议校验仅接受框架内置的 7 种消息类型，自定义事件校验结果为 `False`；而插件总线的 `emit()` 不做任何校验，任意 dict 均可广播。两条通路的契约不同，但缺少文档说明。
- **证据**：`runtime/protocol.py:118-127`（未知 type 返回 `False`，**不抛异常**）；`plugin.py:180-188`。实测：

  ```
  validate_message({'type': 'snapshot'})       → True
  validate_message({'type': 'chat_line'})      → True
  validate_message({'type': 'advisor_result'}) → False
  ```

- **对本案例的影响**：自定义事件（`run_start` / `advisor_result` / `run_end`）若经由协议线校验将被判为不合规。
- **应对**：改走插件总线（不校验），不经过协议线。此即 §3.1 中"插件总线用满"的组成部分。
- **建议**：在 `protocol.py` 文档中明确"本校验仅覆盖框架内置消息，扩展事件请走插件总线"，或为未知 type 提供可配置的放行策略。**属纯文档改动。**

#### G6 `Scratch` 的借用成本偏高

- **严重度**：低（人体工程）｜已绕开
- **现象**：`Scratch(name, currently, config, timer=None)` 要求三个位置参数，而 `build_prompt(template, data)` 一个都不使用；模板目录在 `__init__` 时被读取一次并固化为实例属性。
- **证据**：`prompt/scratch.py:21-36`。实测：

  ```
  改完文件内容后 build_prompt → 'V2'（文件每次重读，改措辞不用重启）
  改环境变量后 template_path 仍是 → C:\...\mavis-tmpl-xxx（目录冻结，换目录得重建实例）
  ```

  附带确认一项正向性质：**模板文件内容在每次渲染时重读**，因此修改措辞无需重启进程。
- **对本案例的影响**：仅需模板填充能力的接入方必须传入三个无意义参数；需要两套模板目录时必须构造两个实例。
- **应对**：`mavis_bridge.prompt_renderer()` 内按目录缓存实例，目录变化时自动重建；三个占位参数集中在一处传入。
- **建议**：为 `Scratch` 增加 `template_dir` 关键字参数；或将渲染拆解为不依赖 `name` / `currently` / `config` 的类方法。

#### G7 `get_summary()` 的 `R` 字段语义具有误导性

- **严重度**：中（可观测性）｜**影响本案例**
- **现象**：`get_summary()` 返回形如 `S:成功,F:最终失败/R:?` 的计数串。字面上 `R` 最容易被读作 "Retry"，但其实际含义是在**成功获得响应**时才递增的计数（`_summary[caller][0] += 1` 位于 `try` 块内、`_completion_timeout` 之后），抛出异常的尝试完全不计入。因此它既不是重试次数，也不等于尝试总数。
- **证据**：`runtime/llm_providers.py:70-94、125-129`。实测：

  ```
  一次成功                 → S:1,F:0/R:1     （R = 完成的请求数）
  3 次异常后放弃（retry=3） → S:0,F:1/R:0     ← 实际发出 3 次请求，R 却是 0
  ```

- **对本案例的影响**：前端仪表最初将该列标注为"重试"，属于**直接读错**——上游全部失败时显示"重试 0 次"，恰好掩盖了最需要被察觉的故障。
- **应对**：① 将界面标签改为"请求"，并注明"抛异常的尝试不计入"；② 需要判定失败性质时不依据 `R`，而依据自身传入 `failsafe` 所得的 `error` / `empty` 状态；③ 计算成功率使用 `S/(S+F)`。
- **建议**：将 `get_summary()` 的输出键改为自解释命名（`success` / `failed` / `completed`），或在返回值中增补 `attempts` 字段以记录异常尝试。属输出格式改动，不影响内部逻辑。

### 3.3b 二轮缺口（G8–G12，2026-10-01 补充）

#### G8 上游状态码未检查：错误页被当 JSON 解析

- **严重度**：中（可用性 / 可观测性）｜**影响本案例**
- **现象**：`OpenAIProvider._chat` 对 `requests.post` 的返回直接 `.json()`，从不读 `response.status_code`。上游 500 / 502 返回 HTML 错误页时，`JSONDecodeError` 被 `completion()` 的全捕获吞掉，走"退避 5s → 重试"，HTTP 500 这一事实在最终返回值里**完全不可见**。
- **探针**：假上游 2 次均返回 `HTTP 500 + HTML`；mavis 照常请求 2 次后返回哨兵。
- **建议**：`_chat` 检查 `status_code`，非 2xx 时抛带状态码与响应摘要的异常（供 G3 的 failsafe 语义携带）。

#### G9 输出长度（max_tokens）不可配置；错误 kwargs 退化为静默重试

- **严重度**：中（可用性）｜**影响本案例**
- **现象**：`_chat` 构造的请求参数不含 `max_tokens`，长输出按端点默认截断；更糟的是 `completion(**kwargs)` 会把未知关键字一路转发到 `_completion(prompt, return_type, temperature=0.5)`，在那里触发 `TypeError` —— 被 G3 的全捕获当作"调用失败"，退化为 `sleep(5)` × retry 的空转。
- **探针**：`completion(..., max_tokens=512, retry=2)` → 上游被调 **0** 次、退避 `[5, 5]`、返回哨兵。一个拼对名字的合法参数不是被忽略，而是把整次调用变成静默空转。
- **建议**：`_chat` 增设 `max_tokens` 透传；`completion()` 对未知 kwargs **当场抛 TypeError**（fail fast），不要让调用方用 5 秒一次的代价发现拼写错误。

#### G10 无流式支持：token 级输出不可表达

- **严重度**：中（可用性）｜**影响本案例**
- **现象**：`_chat` 请求参数硬编码 `"stream": False`；`completion()` 返回 `str`，无迭代器形态。
- **后果**：接入方只能做"整段完成后一次性交付"。ai-debater 的 SSE 是"每路参谋"粒度——无法细化到逐字，现场"看着 AI 打字"的体验在框架层就被排除了。
- **建议**：增加 `completion_stream()` 平行接口（保持 `completion()` 语义不变），回调或生成器两种形态均可。

#### G11 provider 工厂封闭：if/elif 硬编码，无注册钩子

- **严重度**：中（可用性）｜**影响本案例**
- **现象**：`create_llm_provider()` 仅 if/elif 两个分支（ollama / openai），未命中抛 `NotImplementedError`，源码中不存在任何注册钩子。
- **后果**：接入方要支持新协议（如原生 Anthropic）只能改框架源码——与"不 fork 即可扩展"的框架定位冲突。ai-debater 为此被迫自建整个协议桥（`llm_bridge.py`）。
- **建议**：增设 `register_provider(name, factory)`（默认行为不变），或允许经配置注入工厂路径。

#### G12 框架 logger 直写宿主 stdout

- **严重度**：低（人体工程）｜**影响本案例**
- **现象**：`get_logger()` 的 `StreamHandler` 绑定 `sys.stdout`。作为**库**被宿主进程 import 后，框架日志直接污染宿主的受控输出——ai-debater 的机器可读探针（`--json`）被迫先 `logging.disable(CRITICAL)` 才能输出干净 JSON。
- **建议**：库模式默认 `NullHandler` + 显式开关，或 handler 绑定 `stderr`。

### 3.4 接线注意（N1–N4；N5–N6 为二轮补充）

以下四项不属于框架缺陷，无需修改框架，但接入方应当知悉。

| # | 事项 | 说明 |
|---|---|---|
| N1 | `failsafe` 不传则无法分辨失败类型 | 默认 `None` 下两类失败**并非完全同形**：上游重试耗尽返回 `None`，模型返回空内容返回 `''`。但该差别是实现副产品 —— 任何按空值归并的调用方（本案例的 `out is None or len(out) == 0`）都会把二者记成同一种失败。传入私有哨兵后，"上游重试耗尽"成为可比较的身份（见 §3.1.1a）。该参数已存在于 `LLMProvider` 签名（`runtime/llm.py:15-24`），属"使用正确即无问题" |
| N2 | `cache_stats()` / `disable()` 不在抽象基类中 | `LLMProvider` 仅声明 `completion` / `is_available` / `get_summary`（`llm.py:11-34`），而实现类多出这两项。按抽象契约编程无法获取，本案例以 `getattr` 作为可选能力读取 |
| N3 | 模板中的裸 `$` 会触发异常 | `build_prompt` 使用 `Template.substitute`（非 `safe` 版本）。实测 `'$undefined_var'` → `KeyError`，`'单价 $100'` → `ValueError`。正面效果是模板错误即时暴露；代价是金额与公式须转义为 `$$`。本案例在启动期通过 `preload()` 真实渲染一次，将该类错误提前至启动阶段 |
| N4 | `PluginManager.discover()` 仅自动实例化可无参构造的工厂 | `plugin.py:56-71,117-142`。本案例的插件均需 `session_id` / `out_queue`，因此改由 `mount()` 手工挂载。此为有意设计且已见诸文档，记录为**已知边界** |

| N6 | summary 计数递增在并发闸之外（理论性竞态，未复现丢失） | 源码顺序：`with sem:` 只收缩网络调用，`self._summary[...][0] += 1` 的缩进与之平级，并发递增不受闸保护。本机实测 3 × 6400 次并发递增零丢失（CPython GIL 下窗口极小）——按"缺口须可复现"的纪律不立为缺口，仅记录：高并发接入方不应把 `get_summary()` 当精确计量 |

## 4. 讨论

### 4.1 缺口的结构性分布

七处缺口并非均匀分布于框架各层，而是集中于**接入层的契约表述**：

- 仅 G2 属正确性缺陷，且触发条件（多个 `concurrency` 取值不同的 provider 共存）在本案例中未出现；
- G1、G4 属**能力表达**问题——能力存在，但接入方无法表达或难以发现；
- G3、G7 属**语义表述**问题——机制本身可用，但失败语义与计数语义的表述具有误导性；
- G5、G6 属文档与人体工程，不产生功能影响。

该分布提示：该框架的设计重心在仿真语义的正确实现（其 `Agent` / `Simulator` 一侧的封装相当完整），而对"被外部接入"这一使用场景的接口打磨不足。这与 §3.2 的观察一致——框架隐含地假设使用者是其自身仿真场景。

### 4.2 关于"是否应当修改框架"的讨论

本案例采取的立场是**只走已公开的稳定面，不修改框架源码**（见附录 B）。该立场在方法上保证了结论的内部效度，但需澄清其适用边界：这**不等于**认定框架不应被修改。恰恰相反，本报告的建议清单正是为了向框架侧反馈。

判断何种缺口值得回推框架，本文采用的标准是：**该缺口是否具有"绕不过去"的性质**。依此标准，G1、G4、G7 值得上游修复（修改成本低、受益面广），G2 属应优先修复的正确性问题，G3 可通过参数化解决，G5、G6 属文档与人体工程层面的改进。

二轮缺口（G8–G12）沿用同一标准：G8（状态码）与 G9（kwargs 快速失败）是两处**修复成本极低**的可用性修复——各只改 `_chat` / `completion` 一处几行；G10（流式）工程量最大但决定接入方的产品形态上限；G11（注册钩子）是纯新增接口，能让协议桥这类外围适配层彻底消失；G12 按库的通行惯例改 `NullHandler` 即可。

### 4.3 方法层面的反思

本次检验修正了前一版本的一处方法论错误：以"接入方未使用某能力面"推断"该能力面不可用"。正确的做法是逐个能力面分别给出承载与否及其**理由**，并对"不适用"给出架构性判据而非主观印象（§3.2 即以调度语义与产物类型两项判据替代了"感觉不合适"）。

此外，本次检验发现：**接入方的观测口径本身可能错误**（G7 导致前端将 `R` 标注为"重试"）。这提示框架评估不能只检查"框架是否按契约工作"，还须检查"契约的表述是否会导致接入方得出错误结论"——后者是纯功能性测试覆盖不到的。

---

## 5. 结论与建议

**结论一**：mavis v1.3.3 的基础设施半边可在具备并发、时限与失败语义约束的生产链路中完整承载。其中 `failsafe` 失败哨兵与 `PluginManager` 的逐插件错误隔离承担了不可替代的功能，前者解决了"失败类型不可分辨"这一本案例的核心可观测性需求。

**结论二**：其仿真半边与本案例的任务形态存在架构性错位（调度语义与产物类型两项判据），该错位不可通过配置消解，因此本案例不作硬性适配。

**结论三**：在只读接入的前提下共识别出 7 处缺口与 4 处接线注意。缺口集中于接入层契约的表述，而非核心机制的正确性——唯 G2 属正确性缺陷，且其触发条件在本案例中未出现。

**建议（按优先级）**：

1. **G2** —— 修复并发闸的实例语义错配（按 size 分桶，或固化为进程级配置）；
2. **G1 / G4 / G7** —— 提升接入层的能力表达与语义表述质量（开放缓存白名单、补全顶层导出、自解释计数命名）；
3. **G3** —— 参数化退避策略，并允许调用方选择是否吞掉异常；
4. **G5 / G6** —— 补充契约文档、降低模板面的借用成本。

## 6. 局限

本报告为**单案例研究（single-case study）**，其结论的适用范围受以下限制：

1. **案例数量**：仅一个案例（ai-debater）。框架在其他任务形态下的表现不可由本报告推断。
2. **版本单一**：仅测 v1.3.3 的 commit `511dea0`。框架的后续版本可能已修复部分缺口，本报告不构成对当前版本的判断。
3. **任务形态单一**：受测链路为"短时、并发、无状态、单轮问答"。这是本案例的需求所决定的，也是 §3.2 判据成立的前提；换一种任务形态，仿真半边是否适用需另行评估。
4. **缺口覆盖不完整**：7 处缺口是**在本案例的承载路径上**被触发的缺口，不构成对框架接口的穷尽性审计。未被本案例触达的代码路径未作检验。
5. **领域能力未作评估**：本报告评估的是框架的**工程可承载性**，不涉及其仿真语义（智能体行为的可信度、记忆机制的有效性等）的评价。
6. **样本规模**：探针为单轮执行，未做统计意义上的重复测量。涉及的时序型结论（信号量对象同一性、退避参数序列）为确定性行为，重复测量无必要；但性能相关数值未在本报告中使用。
